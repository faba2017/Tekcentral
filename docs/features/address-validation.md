# Checkout Address Validation

Checkout uses the current Google Places Autocomplete Data API in the browser when `VITE_GOOGLE_MAPS_API_KEY` is configured. Suggestions are restricted to South Africa and one `AutocompleteSessionToken` is retained for an interaction, then replaced after place selection and the terminating Place Details request. The selected place is parsed into separate street, suburb, city, province, postal code, country, place ID and coordinates. Manual entry remains available if Places cannot load.

The browser key must permit the Maps JavaScript API and Places API for the deployed storefront origin. Local development restrictions should include `http://127.0.0.1:5173/*` and, when used, `http://localhost:5173/*`; production restrictions should include only the TekCentral storefront domains. The loader is callback-backed and inserts one Google script per page, then imports the `places` library once.

Before delivery quoting, the browser sends the structured address to `/api/addresses/validate`. The backend alone calls Google Address Validation using `GOOGLE_ADDRESS_VALIDATION_API_KEY`; that key is never returned to the browser. The normalized response is reduced to `VALIDATED`, `NEEDS_CONFIRMATION`, `INVALID`, or `VALIDATION_UNAVAILABLE`, a normalized address, useful identifiers and unresolved concerns. Raw Google responses are not persisted. As of this implementation, Google's Address Validation API rejects South Africa (`ZA`) as an unsupported region; Places selection still works, and the backend records the safe `ADDRESS_VALIDATION_REGION_UNSUPPORTED` category without logging the address or key.

Material corrections require customer confirmation. Invalid addresses block quoting. Unsupported-region or service unavailability does not pretend validation succeeded; a locally complete South African address may continue to the existing shipping estimator with a visible fallback notice. Any address field edit clears validation and the current quote.
